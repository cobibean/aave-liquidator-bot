Aave Liquidator · Performance Brief

Optimizing for Speed

A prioritized, batched plan to cut the time between "a position goes underwater" and "our transaction lands" — so we beat the other bots to it.

Repo: ~/Documents/liquidator(s() Created: 2026-06-03 Updated: 2026-06-03 (Batches 1 & 2 shipped + live) Scope: latency only — not correctness/coverage

TL;DR — the one thing that matters

  • The bot polls every 15 seconds. Positions get liquidated within ~1 block (≈0.25–2s). On these L2s we are structurally too slow to win a contested liquidation, no matter how clean the rest of the code is. This is the headline.
  • Everything else is downstream of that. Faster reaction (per-block / push triggers) is the biggest win; trimming the ~7 sequential RPC calls between "found it" and "sent it" is the second; private RPCs are the enabler for both.
  • You're already most of the way there architecturally — the stratified watchlist + Multicall3 sweep + active-debt index are exactly the primitives a fast bot needs. The gap is the trigger (polling vs. events) and the submit path (serial reads + legacy gas).
  • Plan is in 4 batches below, each independently shippable. Ship Batch 1 only after the current crash-fix / coverage upgrades are confirmed healthy in prod.

Background

How a liquidation race is actually won

Three clocks run in series. We only win if the sum beats the competitor's sum.

ClockWhat it isWhere it livesToday
1. DetectTime from "HF crosses 1.0 on-chain" to "our process notices."bot.js poll loopup to 15s
2. DecideRe-check HF, find debt + collateral, simulate, compute profit floor, build gas.aaveHelpers.js + bot.js attemptLiquidation~1–4s (serial RPC)
3. DeliverSign + broadcast + get included in a block with high enough priority.src/gas.js + provider1+ block, legacy gas

The professional bots we lose to (vanity addresses landing in the same/adjacent block) collapse Detect to ~0 (they react per-block or to the oracle-update tx in the mempool) and Deliver to a single block via private orderflow / aggressive priority fees. Our biggest gap is Detect; our second is the serial RPC chain in Decide.

Reality anchor (from the 2026-06-03 situation report). Over ~16h: Arbitrum 36 liquidations, Base 18, Avalanche 32, Optimism 22 — effectively all taken by competitors. Even with discovery fixed, a 15s poll means we'd only catch the slow ones (positions that sit underwater for many seconds). The fast money requires per-block reaction.

1

React per block, not per 15 seconds

The single highest-leverage change. Cuts Detect from ≤15s to ~1 block. Ship after the current crash-fix is confirmed stable.
1.1

Per-block watchlist re-check

✓ LIVE on Arbitrum · others gated Impact: very high Effort: medium Latency: ≤15s → ~1 block
Done + partially activated. bot.js runWatchlistCheck() behind BLOCK_TRIGGER=true. Runs alongside the 15s poll (which keeps maintaining the watchlist) with a shared per-chain lock.inFlight guard so the two never run concurrently. Honors TEST_MODE. Uses a WS endpoint if configured (1.2), else HTTP block polling. ENABLED LIVE on Arbitrum (2026-06-03) — the one chain with a private RPC (HTTP block-poll on the private endpoint; verified per-block events firing ~1s, restarts=0, 0 throttle errors). The other 4 chains stay on the 15s poll until WebSocket endpoints are funded (public RPCs won't sustain per-block load — the design-doc-approved path is WS push). Flip on per chain via the bot-<chain> compose environment:.

Subscribe to new blocks and re-sweep only the watchlist (the near-threshold, non-dust wallets you already maintain) every block, instead of waiting for the 15s tick. The watchlist is tens–hundreds of addresses, so a Multicall3 sweep of it is ~100–300ms — cheap enough to run per block. Keep the full/warm/cold sweeps on their existing slower cadence to refresh the watchlist.

Today

Every chain does while(true){ getUnhealthyPositions(); sleep(15s) } — bot.js:90–110. A position that crosses HF<1 and is taken in the next block is gone ~14s before we look.

Note: the old aave-liquidator container is gone — use docker compose logs -f bot-<chain>.

Run each chain in its own process (PM2 fork mode, Node worker_threads, or one container per chain) so a heavy Base cold sweep can't freeze Arbitrum's event loop and make us miss its block window.

Today

bot.js:70 runs all 5 chains in one event loop. A CPU-bound decode/encode burst on one chain delays every other chain's block handler — directly observed (Base's sweep spiking Optimism/Arbitrum cycle times to 48–73s).

Change

Parameterize bot.js by a single CHAIN and launch N processes (compose already has the pattern; add one service per chain, or a PM2 ecosystem file). Each gets its own heap cap and its own RPC budget.

Why: per-block reaction is worthless if another chain is hogging the loop at the moment your block arrives. This also isolates OOM/crash blast radius to one chain.

2

Collapse the "Decide" path

Cuts the ~7 serial RPC round-trips between detecting a target and broadcasting. Each saved round-trip is ~100–400ms on a public RPC; this is whole seconds.
2.1

Pre-compute everything you can; parallelize the rest

✓ Shipped & live Impact: high Effort: medium ~1–3s off Decide
Done. In bot.js attemptLiquidation: dropped the redundant getUserHealthFactor read (now uses the sweep's HF via position.healthFactor; callStatic remains the real freshness gate). Gas price fetched once (sharedGasPrice) and threaded through simulate → floor → overrides (getTransactionOverrides gained an optional gasPrice arg, backward-compatible — deploy scripts unaffected). Oracle native+debt prices cached per chain via getOraclePriceCached (ORACLE_PRICE_TTL_MS, default 5s).

The current submit path is a chain of awaits, each waiting on the previous:

// bot.js attemptLiquidation, today (sequential):
getUserHealthFactor()        // re-check HF      — already known from the sweep!
→ callStatic.triggerLiquidation()
→ estimateGas + getGasPrice
→ oracle.getAssetPrice(native) + oracle.getAssetPrice(debt)
→ getTransactionOverrides() → getGasPrice() // AGAIN
→ send

Fixes, in order of payoff:

  • Drop the redundant HF re-check (bot.js:169). The streaming sweep just measured HF + total debt for this exact user moments ago; pass them through instead of a fresh getUserAccountData round-trip. callStatic is the real freshness gate anyway.
  • Fetch gas price once and reuse it. It's fetched in simulateLiquidation (bot.js:133), again in getTransactionOverrides (src/gas.js:5), and again for the floor (bot.js:251). One call, threaded through.
  • Cache the two oracle prices per chain with a short TTL (native + debt asset, bot.js:42). They move on Chainlink heartbeats, not per call — a 2–5s cache is safe and removes 2 reads from the critical path.
  • Parallelize what's left. callStatic (the gate) and the gas/oracle reads (only needed if the gate passes) don't depend on each other — fire them with Promise.all and discard the gas work if the sim reverts.

Why: on a contested liquidation, 4–6 fewer serial public-RPC hops is plausibly 1–3 seconds — often the whole margin between landing in block N vs N+2.

2.2

Batch + parallelize candidate enrichment

✓ Shipped & live Impact: medium-high Effort: medium Big win when multiple targets appear at once
Done via Multicall3 (not UiPoolDataProvider — avoids a new per-chain contract dep). New enrichCandidateBatched() in aaveHelpers.js collapses a candidate's per-reserve getUserReserveData into one aggregate3 batch, deriving primary debt + primary collateral from the same read. The enrichment loop now runs candidates concurrently via mapWithConcurrency (ENRICH_CONCURRENCY, default 10), preserving lowest-HF-first order. Verified byte-identical to the old serial path (12/12 Avalanche wallets, block-pinned) via scripts/testEnrichEquivalence.js.

When a price move makes several positions liquidatable in the same block, we enrich them one at a time, and each enrichment is itself serial RPC.

Today

aaveHelpers.js:1280 loops candidates serially; getPrimaryCollateral/getPrimaryDebtPosition call getReservesList then iterate reserves with per-reserve getUserReserveData awaits (:1009, :1327). For a user with 10 reserves that's ~10+ sequential reads — per candidate.

Change
  • Collapse per-reserve getUserReserveData across all reserves (and across all candidates) into one Multicall3 batch — you already have aggregate3InBatches.
  • Enrich candidates concurrently with the existing mapWithConcurrency helper (aaveHelpers.js:37) instead of the serial for.
  • Prefer the Aave UiPoolDataProvider (getUserReservesData, ABI already imported at aaveHelpers.js:147) — one call returns a user's full reserve picture, replacing the reserve-by-reserve loop.

Why: the lowest-HF target is the one every bot is racing for. If we burn 2s enriching candidate #3 before getting to the urgent #1 (they're sorted, but enrichment is still serial), we can lose it. Parallel enrichment + Multicall makes "found 5, ready to fire on all 5" near-instant.

2.3

Cache static, rarely-changing reads

✓ Shipped & live Impact: low-medium Effort: low Removes warm-path round-trips
Done. getReservesListCached (TTL RESERVES_CACHE_TTL_MS, default 5 min) + getAssetMetadataCached (immutable, cached for the chain's lifetime) added in 2.2 and now also wired into the legacy paths (getDebtPosition, getDebtPositions, getUserReservePositions), so reserves-list + ERC-20 symbol/decimals aren't re-fetched per call. Per-user dynamic reads (getUserReserveData) are intentionally not cached.

Memoize per chain: getReservesList() (changes only when Aave lists a reserve), and ERC-20 symbol()/decimals() (immutable). Refresh on a long interval or on miss.

aaveHelpers.js:1322 and :1367 re-fetch these every time. Small individually, but they're on the enrichment path that runs during the race.

Why: cheap, safe, and compounds with 2.2 — every cached read is one fewer round-trip while the clock is running.

3

Win the "Deliver" step

Getting included this block, with high enough priority to beat a competitor's tx in the same block.
3.1

EIP-1559 gas with an aggressive, tunable priority fee

✓ Shipped & live Impact: medium-high Effort: low Inclusion priority
Done + tuned. src/gas.js getTransactionOverrides returns maxFeePerGas/maxPriorityFeePerGas on 1559 chains (all 5), else legacy. bot.js fetches getFeeData() once and threads it through. Tuning fix (2026-06-03): the priority fee is now driven by the base fee, not the node's flat ~1.5 gwei "suggested tip" (which made every chain bid 2.25 gwei on a near-zero base fee). Now priorityFee = clamp(baseFee × PRIORITY_FEE_MULTIPLE[3], floor MIN_PRIORITY_FEE_GWEI[0.05], cap MAX_PRIORITY_FEE_GWEI[2.25]) + bump; maxFeePerGas = baseFee × BASE_FEE_MULTIPLE[2] + priorityFee. Result: ~45× cheaper on quiet chains (Optimism/Plasma → 0.05 gwei), scales with congestion, capped at the old 2.25 gwei so it never overpays beyond before. All four knobs per-chain overridable. We never knowingly overpay into a loss (minProfit floor budgets PROFIT_SAFETY_MULTIPLE × gas; callStatic gates).

Switch from legacy gasPrice + fixed gwei bump to maxFeePerGas / maxPriorityFeePerGas, with the priority fee set as a (tunable) multiple of the network's recent priority fee. On a profitable liquidation, overpaying gas to win is correct — the bonus dwarfs the gas.

Today

src/gas.js:5–10: gasPrice = getGasPrice() + bumpGwei. A fixed bump doesn't track contention and uses the legacy fee market — you can't outbid on priority when two bots target the same position.

Change

Use provider.getFeeData() (already called in src/gas.js:18), set maxPriorityFeePerGas = max(networkTip × PRIORITY_MULTIPLE, floorTip), and size the cap so total gas stays under the computed profit. Gate the aggressiveness by the position's profitability so we only overpay when it pays.

Why: when our tx and a competitor's land in the same block, ordering is (largely) by priority fee. A flat bump loses that auction; a profitability-scaled tip wins it.

3.2

Local nonce management + non-blocking submission

✓ Shipped (async OFF by default) Impact: medium Effort: medium Multiple targets / fire-and-confirm
Done. New src/nonceManager.js: per-(wallet,chain) NonceManager seeds from getTransactionCount("pending") once, hands out nonces locally (no round-trip per send), resyncs from chain on any send/confirm error, and tracks a bounded in-flight count. Each chain process gets its own manager. Two halves, different defaults: local nonce + the in-flight gate are always on (safe, removes a round-trip); non-blocking submission is opt-in via ASYNC_SEND=true and the concurrency cap is MAX_INFLIGHT_TX (default 1 = the proven one-at-a-time behavior). Unit-tested: sequential + concurrent reserve (no dup), resync, cap, RPC-failure fallback.

Don't block the loop on tx.wait() before handling the next target, and manage the nonce locally so back-to-back sends don't collide or wait on a getTransactionCount round-trip each time.

Today

bot.js:96–102 awaits each attemptLiquidation (which awaits tx.wait() at :278) before the next. With several same-block targets, candidate #2 waits for #1's receipt — by then #2 is gone.

Change

Track nonce in memory per wallet/chain (seed from getTransactionCount("pending") once, increment locally), send all viable candidates without awaiting receipts, and confirm/log out-of-band. Keep a per-chain in-flight cap so we don't nonce-stampede.

Why: turns "one liquidation per block, confirmed serially" into "fire on everything viable immediately." Pairs with 2.2 (parallel enrichment) and 1.3 (per-chain isolation).

4

Frontier — react before HF<1 is even visible

Higher effort / infra-dependent. This is how the bots that always win actually win. Defer until Batches 1–3 prove the pipeline lands sizeable liquidations.
4.1

Oracle-update triggers (price-feed driven)

Impact: high (ceiling) Effort: high Most signal-efficient trigger

HFs drop because a price moved. Subscribe to AnswerUpdated on the Chainlink aggregators behind Aave's reserves; the instant a relevant feed updates, re-check exactly the borrowers exposed to that asset. This tells you to act on the same block the price changes — before a poller or even a per-block sweep would notice the HF cross.

Build a one-time map: reserve → AaveOracle.getSourceOfAsset → Chainlink aggregator, and a reserve → borrower index. On AnswerUpdated, sweep only the affected borrowers. (Doc: docs/event-driven-triggers.md option 2.)

Why: the precise, low-noise version of per-block sweeping. Needs WS RPCs (1.2) and the reserve→borrower index, so it follows Batch 1.

4.2

Mempool / bundle submission (full MEV)

Impact: high (ceiling) Effort: very high Needs dedicated node + relay

To truly tie the pros: watch the mempool for the oracle-update tx and back-run it in the same block via a bundle relay (Flashbots-style, where supported). This is the "land in the same block as the price update" capability.

Why deferred: requires a dedicated node with mempool access and a bundle relay per chain — real infra + cost. Only justified once the bot demonstrably wins sizeable liquidations at the per-block tier. Listed for completeness; not recommended yet.

4.3

Pre-stage near-threshold positions (lower the candidate bar)

Impact: medium Effort: medium Readiness, not raw latency

For wallets hovering just above HF 1.0, pre-fetch and cache their debt + collateral assets so that the moment they cross, the "Decide" step is already done and we go straight to simulate+send. This removes enrichment from the critical path for the targets most likely to flip.

Why: complements 1.1. Per-block sweeping tells us when; pre-staging means there's nothing left to compute when it happens. The situation report explicitly flags "no pre-liquidation preparation for users hovering near liquidation" as a gap.

Instrumentation

How to know any of this worked

You can't tune what you don't measure. Before/while shipping, add timing so each clock is visible:

  • Per-stage timers: log ms for detect→decide→deliver separately (the cycle timer at bot.js:94 only measures the whole sweep). Tag each with chain + block number.
  • Block lag: on every detected liquidation, record currentBlock − blockWhereHFcrossed. This is the north-star metric — drive it toward 0–1.
  • Loss attribution: when a watchlist wallet gets liquidated by someone else, log which block they landed in vs. when our sweep last saw it. Tells you whether you lost on Detect, Decide, or Deliver.
  • Win rate on sizeable targets: reuse scripts/probeMeaningfulCoverage.js as the scoreboard (≥$100 debt). That's the real KPI; latency work only matters if this climbs.
